# Shadow Fox

Менеджер Xray и доменной маршрутизации для роутеров Keenetic. Один статический
бинарник на C, без зависимостей кроме libc, под все архитектуры Keenetic.

За основу взят [HydraRoute](https://github.com/Ground-Zerro/HydraRoute)
Ground-Zerro: его схема маршрутизации через политики Keenetic, форма
правил и подход к перехвату DNS. Спасибо автору — без его работы и
открытых исходников этого проекта не было бы.

Xray слушает SOCKS5 на адресе роутера, штатный компонент Keenetic
«Прокси-клиент» поднимает поверх него подключение `Proxy1`, а домены и
подсети из списков заворачиваются в него через ipset и метку политики.

```
домены/CIDR → ipset → метка политики → Proxy1 → xray socks5 → VLESS
```

## Состояние

Работает и проверено на живом Keenetic Ultra: пакет под три архитектуры с
подписанным фидом, своя сборка ядра Xray, разбор ссылок и подписок,
свой экземпляр ядра под надзором, списки доменов и подсетей, перехват
DNS-ответов, наполнение ipset, маркировка меткой политики, веб-интерфейс
с входом по паролю роутера, на русском и английском. Подробности
решений — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Посмотреть, что демон сделает с системой, ничего не меняя:

```bash
shadowfoxd --dry-run
```

## Сборка

Кросс-компиляторы musl под macOS не существуют, поэтому локально доступны только
юнит-тесты, а бинарники под роутер собираются в контейнере или в CI.

```bash
make check        # юнит-тесты, работают и на macOS
make docker-all   # бинарники и пакеты в контейнере
make feed         # opkg-фид в build/feed
make help         # все цели
```

Если тулчейны musl уже есть в `PATH`:

```bash
make all          # aarch64, mipsel, mips
make ipk-all
```

## Ядро Xray

Xray написан на Go и кросс-компилируется без сторонних тулчейнов — нужен
только `brew install go`. Собирается отдельной командой, потому что это
чужой апстрим с закреплённой версией:

```bash
make xray       # три архитектуры, таблица размеров
make xray-check # проверить, что ядро принимает эталонный конфиг
make xray-ipk   # упаковать в .ipk
```

Пакет ставится в `/opt/sbin/shadowfox-xray`, а не в `/opt/sbin/xray`, чтобы
не конфликтовать со штатным `xray-core` из Entware.

## Требования

- **KeeneticOS 4.1 и новее.** Компонент «Прокси-клиент» появился в
  [3.9](https://support.keenetic.com/titan/kn-1810/en/27239-keeneticos-3-9.html),
  а UDP через SOCKS5 (`interface … proxy socks5-udp`) — в
  [4.1](https://support.keenetic.com/titan/kn-1811/en/32140-keeneticos-4-1.html).
  На прошивках ниже 4.1 (3.9, 4.0) кнопка «Создать» в панели завершится сбоем на этой команде,
  а звонки Telegram и WhatsApp пойдут мимо туннеля. Проверено на
  Keenetic KN-1811 (aarch64) и Viva KN-1910 (mipsel).
- **Компоненты роутера** «OPKG» и «Прокси-клиент» установлены
  («Общие настройки» → «Изменить набор компонентов»).
- **Entware** на USB-накопителе с ext4 либо во внутренней памяти — её
  предлагают модели со 128 МБ флеш начиная с KeeneticOS 3.7. В `/opt`
  нужно около 35 МБ: ядро Xray занимает 30 МБ на диске, сам пакет меньше
  мегабайта, плюс зависимости `ipset`, `iptables`, `ip-full`, `conntrack`,
  `openssl-util`.
- **Архитектуры** aarch64, mipsel и mips — все, на которые ставится
  Entware; фид собирается под каждую.

## Установка на роутер

Сначала научить `opkg` ходить по https. Он качает через `wget`, а
встроенный в BusyBox не умеет TLS и обрывается на
`wget: not an http or ftp url`. Корневые сертификаты нужны отдельно: в
зависимостях `wget-ssl` их нет, и без них он возвращает код 5 —
«не проверить сертификат»:

```bash
opkg update && opkg install wget-ssl ca-bundle
```

Дальше подключить фид и поставить пакет. Каталог фида у Entware
называется не так, как архитектура, поэтому он определяется по
`entware_release`:

```bash
ARCH=$(grep '^arch=' /opt/etc/entware_release | cut -d= -f2); case "$ARCH" in aarch64) DIR=aarch64-k3.10 ;; mipsel) DIR=mipselsf-k3.4 ;; mips) DIR=mipssf-k3.4 ;; *) echo "неизвестная архитектура: $ARCH" >&2; false ;; esac && mkdir -p /opt/etc/opkg && echo "src/gz shadowfox https://skunkbg.github.io/shadowfox/keenetic/$DIR" > /opt/etc/opkg/shadowfox.conf && opkg update && opkg install shadowfox
```

На свежем Entware нет ни `curl`, ни `wget` с TLS, поэтому команда
обходится одним `opkg`. Если `curl` уже стоит, то же самое делает
скрипт, который вдобавок проверяет, что фид вообще опубликован:

```bash
curl -fsSL https://skunkbg.github.io/shadowfox/add-repo.sh -o /tmp/sf.sh && sh /tmp/sf.sh && opkg update && opkg install shadowfox
```

Скрипт скачивается в файл, а не подаётся в `sh` через конвейер, намеренно:
у конвейера код возврата берётся от последней команды, а `sh` с пустым
вводом завершается успешно. Из-за этого `curl … | sh && opkg install`
продолжает работу даже когда скачать ничего не удалось.

Управление — через симлинк `shadowfox`, созданный при установке:

```bash
shadowfox start | stop | restart | status
```

Полная картина одной командой: что прочитано из списков, куда заворачивается
каждая группа, сколько адресов в наборах, работает ли своё ядро, что видит
перехват и срабатывают ли правила.

```bash
shadowfoxd --status
```

Обновить после новой сборки — кнопкой на странице или из консоли:

```bash
shadowfox-update upgrade
```

Каждый прогон CI выпускает пакет с новой ревизией (`0.1.0-<номер прогона>`),
поэтому обновление видно сразу. Ручной `opkg upgrade shadowfox` тоже
сработает, но подпись не проверит — см. ниже.

### Подпись фида

Индекс фида (`Packages`) подписан ключом Ed25519, а у каждого пакета в
индексе есть SHA-256. `shadowfox-update` скачивает индекс и подпись,
проверяет её вшитым в пакет открытым ключом (`keys/shadowfox.pub`), сверяет
SHA-256 скачанного пакета и только потом отдаёт файл opkg. Подмена фида,
индекса или пакета останавливает обновление с внятной причиной — кнопка
«Проверить» на странице её покажет.

Первая установка идёт через `opkg` и доверяет только TLS: ключа на
роутере ещё нет. Всё последующее проверяется подписью. Сам opkg подписи
не проверяет: его проверка либо для всех фидов, либо ни для одного, а
фиды Entware не подписаны.

Закрытый ключ живёт только в секрете `SIGN_KEY` репозитория; без него CI
не соберёт фид. Проверка (`openssl pkeyutl -verify`) и подпись идут
штатным OpenSSL из пакета `openssl-util`, своей криптографии здесь нет.

Удалить полностью — вместе с настройками, журналом и подключённым фидом:

```bash
curl -fsSL https://skunkbg.github.io/shadowfox/uninstall.sh -o /tmp/sfrm.sh && sh /tmp/sfrm.sh
```

Одного `opkg remove shadowfox` для установки начисто мало: файлы настроек
пакету не принадлежат — они создаются при первой установке и переживают
удаление, как и журнал с записью о репозитории.

## Веб-интерфейс

После установки открывается по адресу роутера:

```
http://192.168.1.1:8090
```

Там же правятся домены, серверы и подсети — всё, что ниже описано файлами,
можно делать через страницу.

Чтобы интерфейс открывался и снаружи, по поддомену твоего доменного имени
Keenetic:

```bash
shadowfoxd --setup-web
```

Команда печатает команды `ndmc`, которые надо выполнить самому. После них
роутер сам делает HTTPS и спрашивает **логин с паролем от роутера** — своей
проверки входа у Shadow Fox нет и не требуется.

Локальный порт пароля не спрашивает. Если это нежелательно,
`webToken` в настройках включает проверку токена, а `webBind=127.0.0.1`
оставляет доступ только через проверенный вход роутера.

## Настройка файлами

Всё то же самое доступно и без интерфейса. После установки демон работает,
но ничего не маршрутизирует: списки пусты. Полная настройка — четыре шага.

### 1. Ссылка на сервер

```bash
printf '%s\n' 'vless://...' > /opt/etc/shadowfox/nodes.txt
chmod 600 /opt/etc/shadowfox/nodes.txt
```

Одинарные кавычки обязательны: в ссылке есть `&`, `?` и `%`. Права `600`
тоже: внутри uuid, то есть ключ доступа к серверу.

Вместо ссылки годится адрес подписки — тот же `https://…`, что вставляют
в Happ. Демон скачивает его через `wget-ssl`, раскрывает base64 и
получает список серверов; список перечитывается раз в шесть часов и
хранится в `subscription.cache`, так что после перезагрузки ядро
поднимается и без сети. Ядру отдаётся один сервер из списка — первый,
либо выбранный на странице (файл `server.active`). Все сразу через
балансировщик — только `balancer=yes` в настройках: его наблюдатель
каждые пять минут ходит через каждый сервер, и провайдер это видит.

```bash
printf '%s\n' 'https://panel.example.com/sub/token' > /opt/etc/shadowfox/nodes.txt
```

Несколько ссылок по одной в строке — то же, что подписка: список на
странице, ядру один выбранный. Подписка в base64 тоже принимается.

### 2. Прокси-подключение в Keenetic

```bash
shadowfoxd --setup-proxy
```

Команда ничего не меняет — она печатает команды `ndmc`, которые надо
прочитать и выполнить самому. Они меняют настройки роутера, поэтому
делаются осознанно.

### 3. Политика доступа

В панели роутера: **Приоритеты подключений → Политики доступа**. Создать
политику `ShadowFox` и включить в неё **только** подключение `Shadow-Fox`.

Без этого шага политика получит метку, но заворачивать трафик будет некуда,
и молча себя это не проявит.

### 4. Домены

```bash
cat > /opt/etc/shadowfox/domain.conf <<'EOF'
[media]
interface = ShadowFox
youtube.com
*.ytimg.com
=exact.example.com
EOF

shadowfox restart
```

`interface` — это либо политика Keenetic, либо имя сетевого устройства.
Различаются они сами: если такое устройство есть в системе, трафик
заворачивается прямо в него; иначе метка берётся у роутера через RCI.

Проверить, что получится, ничего не применяя:

```bash
shadowfoxd --dry-run
```

## Файлы

| Путь | Назначение |
|---|---|
| `/opt/bin/shadowfoxd` | демон |
| `/opt/etc/shadowfox/shadowfox.conf` | параметры демона |
| `/opt/etc/shadowfox/domain.conf` | домены и целевые интерфейсы |
| `/opt/etc/shadowfox/ip.list` | статические подсети |
| `/opt/etc/shadowfox/nodes.txt` | ссылки на серверы |
| `/opt/etc/shadowfox/xray.json` | конфиг своего ядра, создаётся демоном |
| `/opt/etc/init.d/S99shadowfox` | автозапуск |
| `/opt/etc/ndm/netfilter.d/015-shadowfox.sh` | восстановление правил |
| `/opt/etc/ndm/ifstatechanged.d/015-shadowfox.sh` | реакция на события интерфейсов |
| `/opt/var/log/shadowfoxd.log` | журнал |
| `/opt/var/run/shadowfoxd.pid` | pid |
| `/opt/var/run/shadowfoxd.status` | состояние для `--status` |

Настройки в `/opt/etc/shadowfox/` переживают обновление пакета.

При первой установке списки создаются из готовых образцов:
группы YouTube, TikTok, Discord и Telegram в политику
`ShadowFox`, плюс подсети Telegram в `ip.list` — его приложения ходят по
зашитым адресам, DNS их не видит. Образцы всегда лежат в
`/opt/etc/shadowfox/presets/`; вернуть их поверх своих списков:

```bash
cp /opt/etc/shadowfox/presets/* /opt/etc/shadowfox/ && shadowfox restart
```

Живой ли туннель, демон видит пассивно, не отправляя ни байта: раз в
полминуты читает состояние TCP-соединений самого ядра с сервером из
`/proc/net/tcp`. Есть установленные — туннель жив; только попытки без
ответа — адрес сервера закрыт для этой линии. Итог в шапке страницы, на
карточке ядра и в `--status`.

Проверки насквозь нет никакой, ни по расписанию, ни по кнопке. Она была в
0.1.0-123 и снята: запрос одинакового размера ровно раз в минуту это
сердцебиение, по которому провайдер распознаёт туннель, и после него
адреса серверов закрывались для линии за минуты. Shadow Fox сам не
создаёт трафика через туннель, точка. Ключ `tunnelProbe` в старых
конфигах принимается и игнорируется.

Страница двуязычная: русский и английский, переключатель в боковой
панели, по умолчанию язык браузера. Перевод накладывается на готовую
разметку словарём, исходник страницы остаётся русским; консоль
`--status` и журнал демона только русские, их читает тот, кто чинит.

Ошибки ядра Xray пишутся в `/tmp/shadowfox-xray.log` — на tmpfs, а не на
накопитель: ядро пишет их само по строке на неудачное соединение, и на
флешке это была бы бессмысленная ежедневная запись. Адреса в журнале
замаскированы наполовину. Число строк и последняя ошибка видны на
странице «Сведения» и в `shadowfoxd --status`; после перезагрузки файл
пуст.

## Как это работает

```
домен из domain.conf
  -> перехват DNS-ответа на интерфейсе локальной сети
    -> адрес в ipset
      -> метка на соединении в mangle/PREROUTING
        -> политика доступа Keenetic
          -> прокси-подключение
            -> свой Xray на локальном порту
              -> сервер
```

Перехват пассивный: демон слушает сеть со стороны и не встраивается в
цепочку резолвинга. Если он упадёт, маршрутизация перестанет обновляться,
но DNS у всей сети продолжит работать.

Записи в наборах стареют — по умолчанию за 6 часов. Домен, который перестали
резолвить, выпадает сам, и набор не копит адреса, давно переехавшие к другим
сервисам.

## Сигналы

| Сигнал | Действие |
|---|---|
| `SIGTERM`, `SIGINT` | корректное завершение |
| `SIGHUP` | перечитать конфиг, переоткрыть журнал |
| `SIGUSR1` | восстановить правила — шлют ndm-хуки роутера |
